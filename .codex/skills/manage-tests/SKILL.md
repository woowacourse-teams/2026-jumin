# 테스트 관리

테스트에 영향을 주는 구현·수정·리팩터링·리뷰, 소스나 테스트 파일 이동, 테스트 영향 범위 점검에 사용한다. 푸시를 감시하거나 CI를 자동으로 변경하지 않는다. 별도 요청 없이 커밋이나 PR을 만들지 않는다.

## 최우선 기준

테스트는 코드 구조가 아니라 사용자 행동, API 계약, 도메인 결과를 보호한다. 코드 이동·컴포넌트 분리·의존성 교체·내부 리팩터링 후에도 같은 입력과 행동에서 같은 결과가 나온다면 기존 테스트의 시나리오·검증문·기대값을 유지한다. 구현 파일이 바뀌었거나 테스트가 실패했다는 이유만으로 테스트를 수정하지 않는다.

기존 테스트를 고치기 전에 달라진 외부 동작이나 계약을 한 문장으로 확인한다. 달라진 것이 없다면 구현이나 실행 환경을 먼저 조사한다. 파일 이동에 따른 import·실행 경로 수정과 새로운 공통 UI를 통과하기 위한 테스트 준비 동작은 필요한 만큼만 바꾸고, 기존 결과 단언은 유지한다.

## 무엇을 검증할 것인가

이 저장소에서는 다음 테스트를 우선한다.

- MSW를 이용한 API 요청 흐름과 백엔드 계약 검증: HTTP 메서드, URL, 요청 데이터, 성공·오류 응답, 응답 스키마.
- 커스텀 훅의 동작: 비동기 상태 전환, 낙관적 업데이트, 디바운스, 요청 취소, 오류 복구.
- 순수 함수와 도메인 규칙: 경계값과 데이터 변환.
- 핵심 사용자 흐름을 확인하는 소수의 E2E 테스트.

컴포넌트가 렌더링되는지, 고정된 문구나 아이콘이 존재하는지, 특정 CSS 클래스·`data-*` 속성·DOM 구조·스타일이 적용되는지만 확인하는 테스트는 추가하지 않는다. 시각적 확인과 핵심 사용자 흐름은 Storybook이나 E2E가 도입되어 있거나 이미 해당 동작을 다룰 때 그 도구로 검증한다.

## 테스트 파일 위치

사용자가 다른 구조를 선택하지 않았다면 새 테스트는 아래 위치에 둔다. 파일이 실제로 실행되는지는 현재 실행 설정과 `client/package.json`을 읽고 확인한다.

| 위치 | 역할 | 실행 도구 |
| --- | --- | --- |
| `client/__tests__/unit/` | 개별 규칙, 데이터 변환, 설정의 동작 검증 | `package.json`의 명령으로 Node 내장 테스트 실행기 사용. 기존 파일은 `.test.mjs` 형식 |
| `client/__tests__/integration/` | API·훅·컴포넌트가 연결되어 동작하는지 검증. MSW를 이용한 요청 흐름 포함 | Jest. 기존 파일은 `.integration.test.ts` 또는 `.integration.test.tsx` 형식 |
| `client/__tests__/e2e/` | 브라우저에서 핵심 사용자 흐름 검증 | Playwright. `client/playwright.config.ts`의 `testDir`로 탐색 위치 지정 |
| `client/mocks/` | 개발용 앱과 테스트가 함께 사용하는 API 핸들러와 응답 데이터 | 테스트를 지원하는 코드이며 테스트 종류별 폴더에 해당하지 않음 |

테스트 종류는 실제로 검증하는 동작과 연결 범위로 판단한다. 파일명, 실행 도구, import한 모듈 개수만으로 판단하지 않는다. 여러 테스트 종류가 함께 사용하는 보조 함수와 초기 설정은 종류별 폴더 바깥에 둔다. 테스트에서 사용한다는 이유만으로 `mocks`를 테스트 전용 폴더로 옮기지 않는다.

`playwright-report/`와 `test-results/`는 테스트 소스가 아닌 자동 생성 결과물이므로 Git 추적에서 제외한다.

## 작업 절차

### 1. 테스트를 수정하기 전에 변경 범위를 확인한다

구현 코드의 변경 내역, 주변 코드, 테스트 설정, `package.json`의 실행 명령을 읽는다. 변경이 다음 중 어디에 해당하는지 판단한다.

- 외부에서 관찰할 수 있는 동작이 유지되는 내부 리팩터링.
- 외부에서 관찰할 수 있는 동작이나 API 계약의 변경.
- 잘못된 동작을 의도적으로 바로잡는 버그 수정.
- 기존 테스트가 다루지 않는 새 분기나 도메인 규칙의 추가.

이 판단에 따라 테스트를 유지·수정·추가·삭제한다. 기존 테스트가 실패하면 구현 오류, 실행 환경·외부 의존성, 테스트의 내부 구현 의존성, 실제 계약 변경 중 무엇인지 증거로 구분한다. 기존 구현에서도 발생하던 실패인지 확인해 이번 변경의 영향으로 단정하지 않는다.

### 2. 영향을 받는 테스트를 찾는다

변경한 모듈을 import하는 테스트, 변경한 훅이나 함수를 사용하는 테스트, 같은 API 경로를 호출하는 테스트, 변경한 동작을 검증하는 테스트를 찾는다. 테스트 보조 함수, MSW 핸들러, 응답 데이터, 실행할 테스트를 선택하는 명령도 확인한다.

서비스 진입 시 표시되는 모달·공통 레이아웃·라우트·Provider처럼 여러 진입 흐름에 영향을 주는 변경은 직접 import가 없는 사용자 흐름도 살핀다. 수정한 테스트 파일은 그 파일 전체가 실행 대상이다. 근처 컴포넌트를 렌더링한다는 이유만으로 영향 대상에 포함하지 않는다. 변경된 동작이나 계약에 의존하는지를 기준으로 판단한다.

### 3. 요구사항을 확인하는 데 필요한 범위를 검증한다

- API는 MSW로 요청과 응답을 검증한다. 쿼리 캐시 키의 내부 구조나 클라이언트 내부 호출에 검증을 묶지 않는다.
- 커스텀 훅은 반환값과 외부에 나타나는 동작으로 검증한다. React 훅 자체나 내부 상태 변경 함수를 모킹하지 않는다.
- 순수 함수는 대표 입력, 경계값, 실패 사례로 검증한다.
- 사용자에게 보이는 동작은 의미 있는 사용자 흐름일 때 검증한다. 모든 컴포넌트에 렌더링 확인 테스트를 일괄 추가하지 않는다.

테스트 이름은 내부 함수 호출보다 입력·행동·관찰 가능한 결과를 설명한다. 결과를 확인할 때는 우연히 같은 단어가 다른 곳에 나타나도 통과하지 않도록 대상 영역과 기대 결과를 특정한다. 접근 가능한 역할·이름·레이블을 우선 사용하되, 문구 자체가 계약이 아니라면 복사 문구에 검증을 묶지 않는다. 의미 있는 접근성 쿼리가 없고 안정적인 식별자가 필요할 때만 `data-testid`를 사용한다.

비동기 UI는 Testing Library의 `findBy*` 또는 Playwright locator와 `expect`의 자동 대기로 확인한다. `waitFor` 안에서 클릭·입력·요청처럼 반복되면 안 되는 동작을 실행하지 않는다.

앱이 표시하는 오류 문구를 검증할 때는 저장소의 기존 메시지 상수를 재사용한다. `API_ERROR_MESSAGES` 같은 기능별 상수를 찾아 기대값이나 MSW 응답 설정에서 사용한다. 서버가 보낸 문구를 그대로 전달하거나 변환하는 동작 자체를 검증할 때만 문구를 직접 작성하고, 그 이유를 명시한다. 앱의 기본 오류 문구를 중복 작성하는 용도로 사용하지 않는다.

`location.state`의 내부 구조, 비공개 보조 함수 이름, 내부 호출 순서, React 상태 변경 함수 호출, 쿼리 캐시 내부 상태, CSS 선택자, 지도 SDK 마커의 픽셀 크기, 부수적인 DOM 구조에 의존하는 검증을 피한다. 해당 항목 자체가 요구사항에 포함된다면 유지하는 이유를 기록한다.

### 4. 필요한 테스트만 변경한다

- 내부 리팩터링에서는 기존 시나리오·검증문·기대값을 유지한다. 구현이 올바른데 테스트가 내부 구조에 묶여 실패한다는 증거가 있을 때만 그 결합을 제거하고 이전 동작의 검증은 보존한다.
- 소스나 테스트 파일을 옮길 때는 기존 테스트 사례와 검증문을 보존한다. 영향을 받는 import, 테스트 실행 경로, `package.json` 명령, CI 참조 경로를 수정한다. Jest 테스트뿐 아니라 Node로 실행하는 `.mjs` 단위 테스트도 확인한다. 앱 타입 검사를 통과해도 이 테스트들의 import 경로가 올바르다고 볼 수는 없다. 삭제된 파일은 다른 위치로 이동했는지 먼저 찾고, 사용자의 삭제 의도를 파악하지 않은 채 복원하지 않는다.
- 요구사항, 사용자에게 보이는 동작, API 계약이 바뀌거나 잘못된 결과를 의도적으로 바로잡을 때만 기대값을 바꾼다.
- 새 API 분기, 도메인 규칙, 경계값, 비동기 실패 경로, 기존 버그의 재발 방지를 다루는 테스트가 없다면 추가한다.
- 새로운 공통 모달 등이 기존 E2E 흐름을 막는다면 진입에 필요한 동작만 공통 준비 단계에 추가한다. 기존 흐름의 결과 단언은 유지하고 새 동작은 별도 테스트에서 검증한다.
- 단순 렌더링 테스트가 동작을 검증하지 않는다면 삭제할 수 있다. 삭제 전에 검증할 가치가 있는 동작이 API·훅·순수 함수·E2E 테스트 중 적절한 곳에서 다뤄지는지 확인한다.
- 내부 구현에 과도하게 의존하는 테스트는 동작을 검증하도록 바꾼다. 통과시키기 위해 검증을 느슨하게 만들지 않는다.

실패한 테스트를 통과시키려고 의미 있는 회귀 테스트를 삭제하거나 건너뛰지 않는다. 검증을 느슨하게 만들거나 기대값을 임의로 바꾸지 않는다. 구현이 잘못됐다면 구현을 고친다. 계약 변경으로 테스트가 잘못됐다면 어떤 계약이 바뀌었는지 결과에 기록한다.

### 5. 좁은 범위부터 실행해 검증한다

영향을 받는 가장 작은 테스트부터 실행한 뒤 수정한 테스트 파일 전체와 관련된 사용자 흐름을 실행한다. 서비스 진입 시 표시되는 모달·공통 레이아웃·라우트·E2E 실행 설정을 변경했다면 전체 E2E를 실행한다. 이후 관련 통합·단위 테스트, 타입 검사, 린트, 포맷 검사를 실행한다. `client/package.json`과 저장소 문서의 명령을 우선 사용한다.

`client`의 `pnpm check`에는 Playwright E2E가 포함되지 않는다. E2E 영향이 있으면 `pnpm test:e2e`를 별도로 실행한다. 일부 E2E만 통과한 상태를 전체 검증 완료로 보고하지 않는다. 실행 환경이나 외부 서비스 때문에 테스트가 실패하면 원인을 조사하고, 기대값을 낮추거나 테스트를 건너뛰어 통과시키지 않는다.

파일을 옮겼다면 실행 결과뿐 아니라 실행 대상 탐색도 확인한다. 이동한 테스트가 누락되거나 중복 실행되지 않아야 한다. 필요하면 Jest의 `--listTests`, Playwright의 `--list`를 사용한다. 단위 테스트는 `package.json`에 개별 파일 경로가 지정되어 있는지도 확인한다.

실행 환경 때문에 명령을 실행하지 못했다면 실제 명령과 실패 원인을 기록한다. 실행하지 않은 검사와 실패한 검사를 통과했다고 쓰지 않는다.

### 6. 변경 이유와 결과를 보고한다

다음 내용을 정리한다.

- 유지·수정·추가·삭제한 테스트.
- 각 변경이 필요한 이유와 검증하는 동작 또는 계약.
- 실행한 명령과 결과. 영향을 받지만 실행하지 못한 범위도 명시한다.
- 남아 있는 위험이나 테스트에서 확인하지 못한 범위.

보고는 테스트가 확인하는 동작과 변경 이유를 중심으로 작성한다. 어떤 내부 구현 의존성을 줄였는지 설명할 수 없다면 테스트가 더 견고해졌다고 주장하지 않는다.

## 상황별 판단 기준

| 상황 | 조치 |
| --- | --- |
| 고정된 UI를 렌더링하는지만 확인 | CI 테스트를 추가하지 않거나 기존 테스트 삭제 검토. 시각적 확인이 필요하면 Storybook 사용 |
| 내부 상태나 라이브러리는 바뀌지만 외부 동작은 동일 | 기존 기대값 유지. 내부 구현에 의존하는 검증만 수정 |
| 소스나 테스트 파일 이동 | 사례와 검증문 보존. 경로 수정 후 테스트 탐색과 실행 확인 |
| API 메서드·URL·요청 데이터·응답·오류 계약 변경 | 해당 계약의 API·MSW 테스트와 응답 데이터 수정 |
| 앱의 오류 문구를 기존 테스트에서 검증 | 기존 메시지 상수 재사용. 같은 문구를 직접 중복 작성하지 않음 |
| 새 함수나 도메인 규칙 추가 | 해당 동작을 확인하는 순수 함수 테스트 추가 |
