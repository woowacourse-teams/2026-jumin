# 운영 피크를 기준으로 viewport·search의 Load Test 요청량 결정

- 상태: Accepted
- 결정일: 2026-10-14
- 범위: viewport·추천 검색의 개별 Load, 혼합 Load, Stress Test
- 대체 결정: 없음
- 관련 자료: [Grafana 지정 기간](https://grafana.jucha.info/d/adwn868/058fad8?from=2026-09-29T23:04:00.936Z&to=2026-10-13T14:33:52.187Z&timezone=browser&var-environment=prod), [노션 부하 근거·측정 기록](https://app.notion.com/p/1-API-Load-Test-3f86a8c6159b80d596a4cc86e5ea4a02)

## 문제와 제약

향후 사용자 수나 출시 후 트래픽 목표가 아직 없다. 과제의 예상 트래픽을 설명할 수 있도록, 기존 운영에서 관측한 피크를 Load Test의 기준으로 사용한다.

viewport는 호출량이 많고, search는 핵심 추천 기능이면서 운영 p95 2.04초·p99 13.8초의 지연이 관측되어 분석 대상으로 선정했다. 이 지표는 대상 선정 근거이며, 병목의 원인은 부하 측정과 서버·DB 분석으로 확인한다.

## 관측 근거

사용자가 지정한 **2026-09-30 08:04:00.936 ~ 2026-10-13 23:33:52.187, 한국 시간** 범위에서 Grafana의 운영 Prometheus 지표를 조회했다.

`http_server_requests_seconds_count`의 **5분 평균 RPS를 1분 간격으로 평가**해 API별 최대값을 찾았다. 따라서 아래 값은 HTTP 완료 카운터에서 계산한 추정 처리율이며, 순간 최대 요청 도착률이나 접근 로그의 정확한 요청 건수가 아니다.

| API | 피크 5분 구간 · 한국 시간 | 관측 피크 RPS | 선택한 RPS |
| --- | --- | ---: | ---: |
| `GET /api/parking/viewport` | 10월 2일 21:07 ~ 21:12 | 0.68148148 | **0.70** |
| `GET /api/parking/search` | 10월 7일 23:42 ~ 23:47 | 0.04814815 | **0.05** |

선택값은 실행 설정을 단순하게 하기 위해 관측값에서 소폭 올린 값이다. 각각 분당 42건, 분당 3건으로 설정할 수 있다. 5분은 이번 지속 부하를 정하기 위한 집계 단위이며, 보편적인 필수 기준은 아니다.

재현에 사용한 Explore Instant 쿼리는 다음과 같다. 하위 쿼리의 1분 간격을 지정하여 Grafana 그래프의 자동 간격 조정으로 피크가 누락되는 것을 피했다. 집계 창 전체가 지정 기간 안에 있도록, 기간 길이에서 5분을 뺀 길이를 사용했다.

```promql
(sum by(uri)(
  rate(http_server_requests_seconds_count{
    environment="prod",
    uri=~"/api/parking/(viewport|search)"
  }[5m])
))[1178691s:1m]
```

## 결정

Load Test는 다음 요청량을 **워밍업 후 10분간 유지**한다. 관측된 5분 피크가 10분 동안 지속되는 상황을 가정한다.

| 테스트 | viewport RPS | search RPS | 10분 예정 요청 수 |
| --- | ---: | ---: | --- |
| viewport 개별 Load | **0.70** | — | viewport 420건 |
| search 개별 Load | — | **0.05** | search 30건 |
| 두 API 혼합 Load | **0.70** | **0.05** | viewport 420건 + search 30건 |

각 API 요청 1건을 k6 반복 1회로 두고, 요청 도착률을 고정하는 방식으로 실행한다. 개선 전후에는 같은 요청량·10분 측정·입력·데이터·자원 제한·준비 절차를 유지한다. API별 응답시간과 실패율의 목표는 테스트 설계에서 별도로 확정한다.

혼합 Load는 **각 API의 피크가 동시에 발생하는 상황을 가정한 보수적인 조건**이다. 각 API의 피크 시각에는 다른 API의 RPS가 0이었다. 두 API가 모두 호출된 구간 중 합산 최대는 10월 2일 10:50 ~ 10:55였으며, viewport 약 0.39630 RPS·search 약 0.01111 RPS였다. 따라서 선택한 혼합 조건을 실측 동시 피크나 실제 요청 비율로 설명하지 않는다.

Load Test로 관측 피크에서의 지연·오류·자원 사용과 개선 효과를 확인한다. 최종 개선 코드의 처리 한계와 과부하 안정성은 이후 Stress Test에서 요청량을 단계적으로 높여 확인한다.

## 결과 해석과 한계

- 기준 부하는 낮다. 이 조건에서 정상 처리되더라도 많은 동시 요청을 감당한다고 결론 내리지 않는다.
- search는 10분에 약 30건이므로 p99와 낮은 실패율을 확정적으로 검증하기 어렵다. 표본 수를 함께 기록하고, 최종 전후 비교는 같은 10분 조건을 반복해 실행 간 변동을 확인한다.
- 관측 피크에서 문제가 드러나지 않으면 그 사실을 기록한다. 더 높은 부하에서 찾은 병목은 Stress 조건과 함께 설명한다.
- 수집값이 없는 구간을 0으로 채우지 않았다. 첫 유효 표본은 viewport 9월 30일 11:10, search 11:36이므로 피크는 수집된 데이터 범위에서 확인한 값이다.
- 로컬의 CPU·메모리 제한을 맞추더라도 AWS의 디스크 성능·네트워크·CPU 크레딧까지 재현되지는 않는다. 측정 결과는 해당 로컬 환경의 결과로 해석한다.
- 정리 전 원본 자료는 저장소 밖 보관본의 `server/loadtest/results/traffic-peak-20261014/`에 원래 상대경로로 남겼다. 결정의 핵심 근거와 재현 쿼리는 이 문서에도 유지한다.

## 재검토 조건

출시 후 트래픽 목표가 생기거나, 운영 피크·API 사용 비율·서버 사양이 달라지면 기준 부하를 다시 산정한다. 짧은 요청 집중이나 search의 표본 부족을 별도로 검증할 필요가 생기면 목적을 명시해 추가 조건을 설계한다. 개선 전후 비교 도중에는 기준을 바꾸지 않으며, 바뀐 조건은 별도 실험으로 기록한다.
